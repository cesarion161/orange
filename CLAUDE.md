# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

- **`orange/`** — Java 27 / Spring Boot 4 coordinator. Owns persistence (Postgres + Flyway + jOOQ), task state and the run loop: it starts Claude Code (`claude -p`) directly, one process per agent run, verifies the work itself and integrates it. No Temporal, no external workers.
- **`orange/worker/`** — the image contained runs start from: `Dockerfile` (Claude Code at a pinned version, git, ripgrep, a user that is not root) and `build.sh`, which builds it on the host that uses it, with the uid of whoever builds.
- **`plugin/`** — the Claude Code plugin, everything the laptop runs: the session reporter (`hooks/hooks.json`, `hooks/orange-report.py`; it also marks the steering tab and gives it its start context), the steering MCP entry (`.mcp.json`: every tool of `/mcp/steering`, the task tools included) and the `orange` skill (the steering tab's flow). The repo root is its marketplace (`.claude-plugin/marketplace.json`, name `orange-local`).
- **`deploy/`** — the VPS deploy (remote-first spec R3): `deploy.sh` (run from the laptop), `push-secrets.sh`, and under `vps/` what runs there: `setup.sh`, `compose.yaml` (Postgres, ntfy), `orange.service`, ntfy's config. `deploy/README.md` says what it does and where everything lives.
- **`docs/superpowers/`** — the v2 design spec, the project-space spec that amends it, and per-PR implementation plans.

Inside `orange/src/main/java/com/ai/orange/`:
- **`run/`** — the run loop. `RunRepository` (runs with leases), `TaskReactor` + `ReactorDecision` (each task's next run), `RunScheduler` (per-kind slots), `RunReaper` (expired leases, orphans of a previous instance), and the three executors: `WorkerRunner` (agent runs), `EvidenceRunner` (verify) and `Integrator` (integrate). `RunPreparer` builds prompts, `RunWorkspaces` gives a contained run its clone and brings its commits home, `PostRunSteps` applies a run's effects, `FailureReasons` classifies failures, `SchedulerPause` is the stop switch, `SpendSync` and `RunRetention` keep house.
- **`harness/`** — harness-neutral run model (`RunSpec`, `RunEvent`, `HarnessAdapter`, `ProcessRunHandle`, and `Sandbox`: the run's process lives in a container), **`harness/claude/`**, the Claude Code adapter (`ClaudeCodeCommand` builds argv + env, `StreamJsonParser` reads `--output-format stream-json`), and **`harness/container/`**, the container runtime: `RunnerProperties` (`orange.runner`), `ContainerSpec` (one command in a container of its own), `DockerCommand` (the pure `docker run` command line), `ContainerRuntime` (starts and removes containers, owns the run network) and `ContainerUrls` (a loopback URL as a container has to spell it).
- **`roles/`** — `RolePrompts` (role instructions from `src/main/resources/roles/*.md`) and `ToolPolicy` (tools per run kind).
- **`mcp/`** — the worker MCP endpoint `/mcp/worker` (`WorkerTools`: `report_result`, `request_human`, `submit_review`, the judge's `judge_continue` / `judge_verify` / `judge_escalate` / `judge_idle` and `propose_item`, the brief's `submit_brief`) with per-run bearer tokens.
- **`project/`** — projects, their repos and the project space: `ProjectService` (repo → project, proposed projects), `ProjectCreation` (`orange_project_create`: a project on an existing or a new GitHub repo, active at once), `SpaceService` (goals, milestones, decisions, notes, questions; items supersede, agents only propose) and `Conventions` (session → project → global).
- **`session/`** — the user's own interactive sessions: `NeutralEvent` (what reporters post), `SessionReactor` (the pure rule table), `SessionService` (applies events, files attention), `SessionSweeper`, `QuestionDetector`, `SessionJudgement` (the judge's verdicts) and `SessionClosing` (verify, review, integrate and close a session's work).
- **`attention/`** — the attention inbox (`AttentionService`): everything that wants the user, once per dedupe key. An `AttentionResolver` says what an answer does to its kinds of item (a plan's approval, a stuck task).
- **`planner/`** — plans: `PlannerService` runs the planner (a `plan` run) and reads its `plan.json` (`PlanJson`), `PlanGraphService` ingests a plan as tasks, `PlannerPrompt` is what the planner is told, `PlanService` plans a project's request in the background and then dispatches it or asks, `PlanApproval` (pure) decides which, `PlanText` words the approval item, `Plan` and `PlanRepository` are the `plans` table.
- **`task/`** — tasks and their DAG (`TaskService`, `TaskRepository`, `TaskEventRepository`, `DagValidator`), `TaskAttention` (a stuck task files an item, and the answer reopens it) and `StuckBranches` (a stuck task's branch on GitHub).
- **`status/`** — what is in flight: `StatusService` reads it (`StatusReport`), `StatusText` words it for `orange_status` and for the steering tab's start context (`GET /steering/context`, `api/SteeringController`).
- **`notify/`** — `PushPlanner` (urgency, batch window, quiet hours), `NtfyClient` (a push may carry a link), `AttentionNotifier`.
- **`brief/`** — the focus brief: `BriefSnapshots` reads the facts in SQL (`BriefSnapshot`), `BriefSchedule` and `Quiet` are the pure rules (which brief time is due, when a project is quiet), `BriefService` writes a brief (`BriefPrompt`, `BriefContent`), `BriefScheduler` ticks, `BriefDelivery` pushes, `BriefText` renders the text, the push and the page, `BriefLinks` knows where the page is. `MilestoneTracks` reads each milestone's tasks through its supersede chain and `OnTrack` (pure) labels a dated one `on_track` or `behind`; the status reads them too.
- **`mcp/`** also holds the steering endpoint `/mcp/steering` (`SteeringTools`: the project space, attention, sessions, `orange_focus` for the brief and the task tools; `EventLines` words a run's events for `orange_tail`).
- **`evidence/`** — evidence rows, the configured evidence commands, the `evidence` convention (`EvidenceCommands`) and `EvidenceDetector` (what a repo suggests).
- **`events/`** — the inbox (webhooks are stored first, processed later) and its processor.
- **`routing/`** — the rule table: role × difficulty × risk × prior failures → tier (model, harness, auth, budget) + effort.
- **`gateway/`** — LiteLLM admin client (per-run virtual keys, spend by alias, timeouts).
- **`billing/`** — price table, cost estimate, plan-limit detection and reset time.
- **`worktree/`** — per-task git worktrees (`WorktreeService`, each from its task's `TaskBase`), the one git helper (`Git`) and how a git command authenticates (`GitAuth`).
- **`repo/`** — GitHub repos (remote-first spec §7.1): `RepoKey` (`owner/name`, parsed from a remote URL), `Repo` and `RepoRepository` (the `repos` table), `Mirrors` (one bare mirror per repo, fetched and pushed one command at a time, with the owner's token), `RepoTaskBases` (a task's mirror and base branch) and `GithubRepos` (creates a private repo through GitHub's REST API, the token only in that request's header).

## Common commands

Run from `orange/`:
- **Run app**: `./gradlew bootRun` — automatically loads `orange/.env` into the process env (see `parseDotEnv()` in `build.gradle.kts`). Copy `orange/.env.example` to start.
- **jOOQ codegen**: runs automatically before `compileJava` via the `nu.studer.jooq` plugin. The `generateJooq` task spins up an embedded Postgres 18 (no Docker needed), runs all Flyway migrations against it, then generates Java sources under `build/generated/sources/jooq/main/java` in package `com.ai.orange.db.jooq`. To regenerate after editing a migration, just `./gradlew generateJooq`.
- **All tests**: `./gradlew test` — JUnit 5 + Testcontainers (Postgres 18). Needs a running Docker daemon and nothing else (no Temporal, no model calls). The run loop and the events processor are off in tests (`src/test/resources/config/application.yaml`); `RunLoopE2EIT` turns them on and takes a task from ready to integrated. `SessionCloseIT` verifies, integrates and closes session work on temporary git repositories. `SessionReporterIT` runs the plugin's real reporter script (needs `python3`) on captured hook payloads from `src/test/resources/hooks`. `BriefIT` takes a brief from its brief time to the phone, with the fake `claude` and a fake ntfy. The container tests (`ContainerRuntimeIT`, `ContainerAdapterIT`, `ContainerRunIT`, `RunLoopE2EIT.InContainers`) start real containers, so they also need the Docker CLI on the `PATH`. On first use they build their own image, `orange-worker-test:local` (a JDK, git and the fake: `src/test/resources/worker-test/Dockerfile`), which needs the network once, and they create the Docker network `orange-runs`.
- **Live tests** (tagged `live`, excluded from `test`): `./gradlew liveTest`.
  - `ClaudeCliContractLiveIT` runs the installed `claude` with orange's full command line and an invalid token (no secret, no model call); rerun it after Claude Code updates itself.
  - `WorkerMcpRealClaudeLiveIT` checks that the real `claude` connects to `/mcp/worker` and sees the run's tools (invalid token, no model call).
  - `SubscriptionSmokeLiveIT` makes one tool-less Haiku call on the Max plan (needs `CLAUDE_CODE_OAUTH_TOKEN`).
  - `ContainerLiveIT` (`./gradlew liveTest --tests '*ContainerLiveIT'`) runs the real worker image in container mode and is skipped until `./worker/build.sh` has built it. The Claude Code in the image takes orange's command line as a user who is not root and reaches `/mcp/worker` from inside a container, and a review runs no hook of the tree it reads (both with an invalid token, no model call); with `CLAUDE_CODE_OAUTH_TOKEN` it also makes one real implement run on the small tier, on a throwaway repo.
  - `LiteLlmGatewayLiveIT` exercises the virtual-key lifecycle and the alias lookups against a running LiteLLM (needs `LITELLM_MASTER_KEY`), with no model calls.
- **Single test class**: `./gradlew test --tests com.ai.orange.run.TaskReactorIT`
- **Build**: `./gradlew build`
- **Worker image** (container mode only): `./worker/build.sh [--base <image>] [--tag <name>] [--claude <version>]` builds `orange-worker:local` on `debian:bookworm-slim`. Run it on the host that runs orange, as the user orange runs as: the image's agent user gets that uid. A repo's toolchain comes with `--base` (any Debian or Ubuntu image that has it); another tag goes into `ORANGE_WORKER_IMAGE`. orange never builds or pulls the image itself.
- **Local infra (Postgres + Grafana LGTM)**: `docker compose up -d`. Postgres is published on `127.0.0.1` only. Spring Boot's `spring-boot-docker-compose` dev dependency also brings these up when running `bootRun` with the `dev` profile.
- **LiteLLM gateway** (only for routing tiers with `auth: gateway`): `docker compose --profile gateway up -d litellm`. It refuses to start without `LITELLM_MASTER_KEY`; `litellm-db-init` creates its database on existing Postgres volumes.
- **Run with Testcontainers-managed Postgres instead of compose**: `./gradlew bootTestRun` using `TestOrangeApplication`.
- **Deploy to the VPS**: `deploy/deploy.sh [host]` (default `orange-vps`, an SSH alias for root) builds the jar, copies it with `deploy/vps/` and `orange/worker/`, sends the secrets, runs `setup.sh` there and checks the result; idempotent, rerun it for every version. `deploy/push-secrets.sh [host]` only sends `CLAUDE_CODE_OAUTH_TOKEN` and `ORANGE_GITHUB_TOKENS` from `orange/.env` again and restarts orange.
- **Forward GitHub webhooks to localhost during dev**: `./scripts/forward-webhooks.sh` (requires `gh` + `gh-webhook` extension; reads `GITHUB_ORG` xor `GITHUB_REPO` and `GITHUB_WEBHOOK_SECRET` from `.env`).

The Java toolchain (JDK 27) is provisioned automatically by the foojay resolver if it isn't installed.

## Architecture

### The run loop
Every unit of agent or verification work is a `runs` row (kinds `plan`, `implement`, `ci_fix`, `verify`, `diff_review`, `integrate`, `judge`, `brief`). A task has at most one queued or running run (partial unique index).
- **`TaskReactor`** reacts to `task_changed` / `run_changed` (and sweeps every `orange.runs.reactor-sweep`). It locks the task row and applies `ReactorDecision`, a pure rule table: `ready` → implement; `running` → a `ci_fix` after verify gaps, an integration conflict or a failed fix, otherwise implement (with review gaps, or the failed attempt's own feedback); `verifying` → verify, then a diff review when `ReviewPolicy` asks for one, then `verified`; `verified` → integrate. Too many failures (`orange.routing.escalation.needs-human-after-failures`) or a worktree that moved under orange → `needs_human`. Nothing happens while paused.
- **`RunScheduler`** claims queued runs (on `run_queued`, when a run ends, and every `scheduler-poll`) up to each kind's slots and `max-concurrent`, and runs each on a virtual thread. Plan and brief runs are started directly (`WorkerRunner.runDirect`): they take no slot and are not queued.
- **Leases**: a running run renews its lease every `heartbeat`; `RunReaper` fails expired leases (`lease_expired`) and, at startup, kills and fails runs a previous instance left running (`coordinator_restart`). Neither counts against the task. In container mode it also removes those runs' containers, found by the label `orange.run=<run id>`, and then the clone they worked on; an expired lease's row is finished first, so a supervisor that is still alive finds the run ended and does not take the docker client's exit for the work's failure.
- **Ordering rule**: a run stays `running` until its post-run steps (`PostRunSteps`) have landed, so the reactor never queues a task's next run on half-applied state.
- **`SchedulerPause`**: failures that would recur at once pause the scheduler — a plan limit until its reset time, a rejected or missing token until resumed, the gateway down for 5 minutes, a missing binary or broken workspace until resumed, and so does Docker that cannot start a run's container (`container_unavailable`: no daemon, no `docker`, no worker image). `GET /scheduler`, `POST /scheduler/pause|resume`.

### Running Claude Code (`WorkerRunner`)
1. **Prepare** (`RunPreparer`): the task's worktree (`WorktreeService.ensure` keeps earlier attempts' commits; it comes from the task's repo's mirror, or for a task of no repo from `orange.worktrees.base-repo`) and a prompt — the task, the operator's reopen note, `input.feedback` to address, how earlier attempts ended, and the base the branch integrates onto. A diff review gets the intent and the whole diff instead (cut at 200,000 characters).
2. **Route** (`RoutingTable`, `orange.routing`) to a tier (model, harness, auth, budget) and an effort. Two failures move the run one tier up (or raise effort at the top tier); risky tasks get at least the large tier.
3. **Credentials** by the tier's `auth`:
   - `subscription` (default): the Max-plan token from `claude setup-token` (`CLAUDE_CODE_OAUTH_TOKEN`); Claude Code talks to Anthropic directly. Anthropic's terms restrict subscription tokens to Claude Code itself, so the token goes only into the `claude` child's environment — never to LiteLLM, logs, `run_events`, `task_events` or `runs`.
   - `gateway`: a LiteLLM virtual key minted for this run (`GatewayClient`), limited to the run's models and budget, always blocked when the run ends; `SpendSync` later books its final spend and deletes it.
4. **MCP**: agent kinds that report get a per-run token (only its SHA-256 is stored) in a `mcp.json` passed as `--mcp-config` and deleted afterwards. Outcomes come only from `/mcp/worker` (`report_result` done|blocked|failed, `request_human`, `submit_review` pass|gaps) — never parsed out of transcripts. Tools per kind come from `ToolPolicy` (implement/ci_fix edit and commit; diff_review is read-only with no Bash).
5. **Start** `claude -p --output-format stream-json --verbose --model … --effort … --setting-sources project,local --strict-mcp-config …`. A `diff_review` gets `--setting-sources user` instead (`ToolPolicy.projectSettings`): the tree it reads is what the reviewed agent committed, and a hook from that tree's `.claude/settings.json` would run with the reviewer's run token in reach and could submit the verdict itself. The prompt goes on **stdin** (never argv). The child environment is built from an allowlist (`orange.harness.claude-code.pass-env`); credential-like variables are dropped even if allowlisted, and `CLAUDE_CONFIG_DIR` points at a per-run directory under `orange.harness.run-root` so the user's own Claude Code login, plugins and hooks never load. The credential and the MCP token are redacted from everything the run writes.
6. **Watch**: events go to `run_events` (`init`, `assistant`, `tool_use`, `tool_result`, `result`, `api_retry`); subscription runs are killed when their estimated cost passes the tier budget; every run is killed at its kind's timeout. Kills take the whole process tree.
7. **Outcome**: no report → `no_outcome`, a `failed` report → `reported_failed`; `FailureReasons` decides what counts (model failures add to `tasks.failures`) and what pauses.

**In a container** (`orange.runner.isolation=container`, and only for a task's runs and the planner's: see Isolation below) the same steps run with these differences:
- **Workspace**: an `implement` or `ci_fix` run does not work in the task's worktree but on a clone of the task's branch under its run directory (`RunWorkspaces.cloneOf`: `--no-local`, the branch and the base ref, no remote, nothing shared with the base repo). A task's `diff_review` gets the worktree mounted read-only.
- **Start**: `WorkerRunner` puts a `Sandbox` on the `RunSpec`, and `ClaudeCodeAdapter` starts the same `claude` command line through `docker run` (`DockerCommand`): `--rm -i --pull never --init`, orange's own uid and gid, `--cap-drop ALL`, `no-new-privileges`, a pids limit, and three mounts at the paths they have on the host (the working directory, the run's `CLAUDE_CONFIG_DIR`, `mcp.json` read-only). Nothing of the host's environment goes in, not even `PATH`. The credential is passed as `--env NAME`: its value is only in the docker client's environment, never in an argv. The MCP URL names the coordinator as `host.docker.internal`.
- **Tools**: coding runs get `--permission-mode bypassPermissions` (`ToolPolicy.inContainer`): the container is the boundary. A review keeps `dontAsk`.
- **Watch**: the process orange supervises is the docker client, which carries stdin in and stdout, stderr and the exit code back, so the stream, redaction, the lease, the budget and the timeout work unchanged. A kill also removes the container (`docker rm -f`, again once the client has gone), and so does every end of the client, before its exit is reported: a docker client can die without its container.
- **Home** (`RunWorkspaces.bringHome`): after a coding run, a second container without network reads the clone and writes one bundle of what the run committed; orange fetches that file into the task's worktree and resets the branch to it. Commits come home from runs that failed, timed out or went over budget too, not from cancelled ones. A run that reports `done` while its commits cannot be brought home fails as `no_commits`. What the agent left uncommitted is deleted with the clone, and the clone only once docker says that none of the run's containers is left (`RunWorkspaces.discard`); otherwise it stays until the run's directory goes.
- **Outcome**: when docker could not start the container (exit 125, 126 or 127 and no result) the run ends `container_unavailable`, which does not count and pauses the scheduler until resumed.

### Verification and integration (project-space spec §7–§8)
An agent's `done` only starts verification; evidence decides "done".
- **Implement done**: with commits on the branch, the head is recorded and the task moves to `verifying`; without, the run fails as `no_commits`.
- **`EvidenceRunner`** (`verify` runs, orange's own code): the worktree must be at the queued head and clean, and every evidence command must pass (a task of a project: the project's `evidence` convention; a task of no project: `orange.evidence.commands`), run as `sh -c` in the worktree with only the allowlisted environment. Each check is an `evidence` row; failures are gaps that send the task back for a `ci_fix` and count. In container mode a task's commands run on a clone of the head under the run's directory, each in a container of its own (`orange-run-<run id>-c<n>`, the worker image, and of orange's environment nothing: only `HOME`); a command docker could not start (exit 125) is no evidence: the run ends `container_unavailable`. A project task whose project asks for evidence and has none in force waits in `verifying` and files one `evidence_missing` item (`EvidenceAsk`); the reactor verifies it once the user puts commands in force.
- **`diff_review`** (optional; remote-first spec §7.3): evidence commands are the gate, and a review runs only when `ReviewPolicy` asks for one. Under the `review` convention (`never`, `risky` (the default) or `always`; tasks read the global value until they have a project), `risky` means a task whose metadata says `review` or `risk`, or whose diff touches `orange.routing.risk.paths` (`RiskPaths`; a diff that cannot be read counts as risky). The planner may set both flags in `plan.json`. A read-only reviewer compares the diff with the intent; its verdict is evidence. `pass` → `verified`; gaps send the task back for rework and count. Without a review, passing checks → `verified`.
- **`Integrator`** (`integrate` runs, merge mode, one at a time): rebase onto the base (a branch that already has the base keeps its SHAs); a changed head goes back to `verifying` (a passing diff review, if there was one, carries over; the commands re-run); otherwise push the base when there is an origin (`orange.integration.remote-push` and the project's `remote-push` convention), through the repo's `Remote`. For a task of the legacy base repo it then moves the local base branch along (`merge --ff-only` in a clean checkout, `update-ref` when not checked out, left alone when dirty); a mirror has no local base. A conflict goes back for a fix without counting; git trouble goes to a person. `integrated` promotes the task's dependents.

### GitHub is the meeting point (remote-first spec §7.1, §7.4)
- **Repos are their remote.** `repos` holds a project's GitHub repos by `owner/name` (lowercased; `RepoKey.parse` reads `https://github.com/o/n`, `git@github.com:o/n`, `ssh://git@github.com/o/n`, with or without `.git`, and anything under `orange.repos.github-url`). A checkout (`project_repos`: a path on a node) links to its repo by its remote, so every checkout of one repo, on any machine, is one project; a new checkout of a known repo joins its project without a proposal. A repo without a GitHub remote is watched as before, but orange cannot close its sessions, and says so once (`repo_not_on_github`). `orange_project_update add_repo` takes `owner/name` (or a checkout's path, as before).
- **Mirrors.** `Mirrors` keeps one bare repository per repo at `orange.repos.root/<owner>/<name>.git`, with GitHub as `origin` and its branches as `origin/*`. Only orange's own git runs in it: task worktrees are added from it, a session's checks and integration use clones and scratch worktrees of it. Clones happen in a temp directory moved into place, so a crash leaves no half-made mirror. Every fetch and push of one repo holds that repo's lock.
- **Tokens.** `orange.repos.tokens` (`ORANGE_GITHUB_TOKENS`, `owner=token[,owner=token]`) holds a fine-grained PAT per owner. `GitAuth` hands it to one git command through a credential helper given with `-c` that reads it from that git process's environment (`ORANGE_GIT_SECRET`): it is in no argv, no remote URL, no config file and no log, and never in a container (agent clones have no remote). Without a token git runs with no credentials at all (a public repo reads fine).
- **Tasks belong to a project and a repo** (`tasks.project_id`, `repo_id`). `POST /tasks`, `POST /dispatch` and `plan.json` (`project`, `repo`; a task may name another `repo` of the same project) place them: `ProjectService.placeTask` takes the repo named, or the project's only repo. A task of a repo branches from, is diffed against and integrates onto `origin/<base>` of its mirror, where the base is the project's `base-branch` convention, else the repo's default branch. Tasks without a project keep the legacy `orange.worktrees.base-repo`. A task of a repo whose project does not push (`remote-push` off) stays `verified`: a mirror has no other base to integrate onto. One repo's or project's trouble is that task's: a mirror that cannot be cloned or fetched, a base branch GitHub lacks or a task of no project without a base repo fails the run `repo_unavailable`, a broken `evidence` convention fails it `bad_convention`; both count against the task (so it reaches a person) and never pause the scheduler. A mirror path that turns out not to be a bare repository is moved aside (`<name>.git.broken-<ms>`), never deleted.

### Isolation (v2 spec §16, PR 6 plan)
`orange.runner.isolation` decides where a task's runs execute.
- **`process`** (the default): an agent is a child process of orange. Claude Code confines its file tools to the worktree, but its Bash tool is not confined, and evidence commands run as orange's user. For local development.
- **`container`**: everything that executes what a task's agent wrote runs in a container that holds one directory of the host and none of orange's environment: `implement` and `ci_fix`, the task's `diff_review` (Claude Code loads the project settings and hooks the agent committed) and each evidence command of its `verify`. `integrate` stays orange's own git in orange's own checkout. A `plan` reads a clone of the project's repo, which agents wrote: in container mode it runs in a container that holds its plan directory (writable, the clone at `repo/` inside it) with its tools (no Bash, so `acceptEdits`); in process mode it stays on the host without `WebFetch` whenever the clone is there. `brief`, `judge` and a session's `verify` and `diff_review` stay on the host as before: they have no tools and an empty directory, or run the user's own commands on the user's own code.
- **The rule**: no container gets write access to a directory in which orange runs git, and orange never runs git in a directory a container wrote. git executes what a repository's config names (`core.fsmonitor`, `core.sshCommand`, `diff.external`), and whoever writes a worktree can replace its `.git`. So the agent's repository is a clone per run that only a container reads, the task's worktree stays orange's, and one bundle file crosses back.
- **The network**: online containers are on `orange.runner.container.network` (`orange-runs`, a bridge orange creates with traffic between containers off; the deploy creates it first, with a fixed subnet) with `host.docker.internal` for the host (`orange.runner.container.host-address`: Docker's `host-gateway`, or on the VPS the run network's gateway, which is where orange listens for runs: `orange.server.extra-addresses` adds a connector per address beside `server.address`); never the host network, never the Docker socket. `config/RunNetworkGuard` answers 403 to every request from that network's subnets except exactly `/mcp/worker`, before the webhook's HMAC filter and the token check see it. The subnets are looked up before the web server starts; while Docker has not answered (asked again every 30 s) the guard lets through only the loopback address and `/mcp/worker`. It reads the connection's address, so do not set `server.forward-headers-strategy` without revisiting it. The export container has no network at all.
- **What the network does not hold**: the internet is open to a run (it talks to Anthropic and fetches dependencies; there is no egress allowlist), so a run can send what it holds anywhere: the repository and its own token, which is in its environment as in process mode. On the VPS the deploy keeps runs off the tailnet, link-local and private addresses (`deploy/vps/run-egress.sh`, rules in the raw table: in FORWARD, Tailscale's chain accepts tailnet traffic first and Docker's bypasses ufw). On Docker Desktop a container's request arrives from 127.0.0.1, so the guard cannot tell it from the user's own and a contained agent reaches the whole open API and everything on the Mac's loopback address: container mode on a laptop is for development and the live check, with `ORANGE_API_TOKEN` set. On Linux the guard rests on Docker's routing (to be checked on the VPS), and a container reaches whatever the host serves on all interfaces.
- **Limits worth knowing**: the worker image is one per deployment and must be built for the uid orange runs as (a coordinator running as root is refused at start); run root and worktree root must be paths the Docker daemon sees as orange does; evidence commands that need Docker themselves (orange's own Testcontainers suite) cannot run; nothing is cached between runs unless `orange.runner.container.volumes` mounts a cache, which every run then shares. At start orange only warns when the network or the image is missing. In process mode an agent's Bash reaches the task's worktree and through its `.git` the repo's mirror, whose config orange's own git reads with the owner's token in its environment: on the VPS, run in container mode. The full list is under "Known limits" in `docs/superpowers/plans/2026-11-10-orange-v2-pr6-containers.md`.

Tests never call a model: `orange/src/test/resources/fake-claude/FakeClaude.java` is a single-file program that speaks real stream-json and the worker MCP protocol, launched via `com.ai.orange.harness.FakeClaude.command()` / `FakeClaude.register(...)`. With `report_result` allowed it implements and commits; with `submit_review` allowed it reviews and passes. With `judge_continue` allowed it answers the session (`judge-verify` says the work is finished; put `[[fake:review-gaps]]` in a committed file to fail a session's diff review). With `submit_brief` allowed it writes a brief for the projects in its prompt. Other scenarios are picked by `[[fake:<name>]]` markers in the prompt (`judge-unsure`, `judge-escalate`, `judge-verify`, `judge-idle`, `judge-propose`, `no-commit`, `report-failed`, `blocked`, `no-outcome`, `dirty`, `wrong-tool`, `review-gaps`, `error`, `hang`, `commit-hang`, `rewind`, `expensive`, `plan-limit`, `auth-failed`, `leak-env`, `report-blocked` (`report_result` blocked; `blocked` is `request_human`), `plan`, `plan-ask`, `plan-risky`, `plan-evidence`, `plan-bad-evidence` (a proposed command with a line break), `plan-milestone:<id>` (the plan scenarios combine; each writes `repo=visible|hidden` and `symlinks=<n>` to `fake-probe.txt` under the run's `CLAUDE_CONFIG_DIR`), `probe`, `brief-urgent`, `brief-unknown-project`, `brief-corrected`). `probe` writes which of the prompt's `probe: <path>` lines it can see to `fake-probe.txt`, then implements. In container mode the same fake runs inside the test image (`com.ai.orange.harness.container.ContainerTestSupport.register(...)`).

### Sessions, the project space and attention (project-space spec, Phase A)
orange also watches the sessions the user runs themselves. Nothing here starts an agent; the judge that answers a stopped session is Phase B.
- **Reporter**: the plugin's hooks run `plugin/hooks/orange-report.py`, which turns a Claude Code hook into a neutral event (`session_started`, `user_prompt`, `stopped`, `waiting`, `active`, `session_ended`) and posts it to `POST /sessions/events`. It resolves git itself (main checkout through the common git dir, worktree, branch, remote; at a stop also the head and the `git status --porcelain` lines, which is all orange ever learns of the checkout), always exits 0 and gives up on an unreachable orange after 2 s, so a session never depends on orange. What it could not send waits on disk (`~/.orange/node/queue/`, one file per event, the newest 1000 of the last 7 days), and the next hook that gets through, whatever its kind, sends the queue first, oldest first, its own event behind it; event ids make a replay idempotent, and an event orange refuses for good (a 4xx but 401/403/408/425/429) is dropped. It prints nothing, except the hook decision that carries orange's answer at a stop (below). `active` comes from PostToolUse, and only while a marker file under `~/.orange/node/waiting/` says the session was waiting.
- **Ingestion**: the controller validates and stores the event in the `events` inbox (source `session`, `delivery_id` = the reporter's event id); `SessionEventHandler` applies it through `SessionService.apply`, so events are idempotent, ordered and retried like webhooks.
- **Rules** (`SessionReactor`, pure): a stop whose last message asks something (`QuestionDetector`) files a `normal` item; so does a permission or input prompt. `SessionSweeper` makes either `urgent` after `orange.attention.waiting-escalate-after` without the user, and files a stop with nothing to ask after `idle-after`. A user prompt, activity or the session's end resolves the session's items. Sessions of an `archived` project file nothing.
- **Projects**: a session's repo decides its project. An unknown repo becomes a `proposed` project plus an attention item; resolving it with `confirm` activates the project, `ignore` archives it.
- **Space**: `space_items` are never edited in place — a change inserts an item that supersedes the old one. An agent's item starts `proposed`; only accepting it makes it active (and only then does a proposed convention replace the value in force).
- **Pushes**: `AttentionNotifier` sends open `urgent` and `critical` items to ntfy (`orange.notify.ntfy`), one push per `batch-window` with everything that queued up; quiet hours (the global `quiet-hours` convention) hold all but `critical`. An item counts as pushed only when ntfy took it. Pushes carry session excerpts, so point it at a server you trust.
- **Steering**: `/mcp/steering` serves `orange_projects`, `orange_project`, `orange_project_create`, `orange_project_update`, `orange_add`, `orange_set`, `orange_accept`, `orange_drop`, `orange_done`, `orange_attention`, `orange_resolve`, `orange_sessions`, `orange_focus` (the brief, below), and the task tools (remote-first spec §7.5, below): `orange_plan {project, request, milestone?}`, `orange_status`, `orange_task {id}`, `orange_tail {id, limit?}`, `orange_cancel {id}`, `orange_pause {reason?}`, `orange_resume`. A task id is a full UUID or 8+ hex characters an id starts or ends with; the short id shown everywhere is the last 8 (uuidv7's first 8 are a timestamp that sibling tasks share). Handlers never throw: a bad call comes back as an error result that says what to correct. REST: `GET /sessions`, `GET /attention`, `POST /attention/{id}/ack|resolve`, `GET /steering/context`.
- **Auth**: with `ORANGE_API_TOKEN` set, the whole operator API needs it as a bearer token (403 without): `/tasks`, `/plans`, `/dispatch`, `/scheduler`, `/runs`, `/events`, `/dev-envs`, `/health`, the actuator but health and info, `/sessions/**`, `/attention/**`, `/mcp/steering`, `/steering/**` and `/brief`. Open are only the probes (`/actuator/health`, `/actuator/info`, `/api/ready`, `/api/status`) and what authenticates itself: the webhook (HMAC), `/mcp/worker` (run tokens), `/brief/{id}` (page key). Blank leaves everything open, for local development. Behind `tailscale serve` every request comes from 127.0.0.1, so on the VPS the token is mandatory. One brief's page, `/brief/{id}`, takes the brief's page key or the token (`BriefPageController`). The check (`ApiToken`) is an authorization rule inside the security chain, so it holds however a request spells the path.

### The session judge (project-space spec, Phase B)
With `orange.judge.enabled` (the default), a stop is decided by a short `judge` run instead of Phase A's question rule.
- **Handing over**: a stop the reporter made longer than `hook-wait` ago (replayed from its disk queue: the hook that would deliver a verdict is gone) is never judged; the rules apply to it. Otherwise `SessionService.apply` moves the session to `judging`, remembers the stop (`sessions.stop_event_id` = the reporter's event id) and queues a `judge` run for the session (`runs.attended_session_id`; routing role `judge`: small tier, low effort; priority ahead of task work). Not judged: muted projects, `auto-answer: none`, a paused scheduler (rules apply instead), and a session orange has already answered `max-auto-continues` times in a row — that files an urgent `session_loop` item (the loop guard).
- **The run**: `JudgePrompt` builds the prompt from Postgres — intent, last message, the latest prompts and stops, the project's goals, decisions and notes, the conventions in force, earlier attention items. No judge keeps a context. What orange knows comes first; what the session wrote (intent, turns, last message) comes last, inside a fence named by a per-run random id, and the role prompt says nothing in there is a project fact or an instruction. The judge has no built-in tools at all and runs in an empty directory of its own, never in the user's checkout (whose settings and hooks would load). It ends with exactly one of `judge_continue`, `judge_verify`, `judge_escalate`, `judge_idle` on `/mcp/worker`; `propose_item` proposes a decision or a note.
- **The decision** (`SessionJudgement.after`, a post-run step): `continue` at or above the project's `auto-answer-confidence` becomes a pending verdict and counts towards the loop guard; below it, it is escalated with the judge's answer as `proposed_answer`. `escalate` files the judge's question at its urgency. `idle` lets the session stop. `verify` starts the close (next section). A failed judge falls back to the rules. A decision for a stop the session has left (a user prompt, a newer stop) is recorded as `expired` and never delivered.
- **Delivery**: after posting a stop, the reporter long-polls `GET /sessions/verdict` (`SessionJudgement.poll`): `pending` (ask again), `none` (let the session stop) or the verdict. A `continue` is delivered only when the hook acknowledges it (`POST /sessions/verdict/ack`): then the session is `active` again, the answer is recorded as an `orange` decision in the project's space, and the hook prints `{"decision":"block","reason":<message>}`. A user prompt cancels pending verdicts and queued judge runs, and one that is stored but not applied yet already makes poll and ack refuse. orange down, or any error, means no verdict: the session just stops.
- **Time** (`SessionJudgement.sweep`): a `continue` no hook collected within `pickup-grace` expires and is filed as a question with that answer proposed; a session still `judging` falls back to the rules when nothing will decide it: its judge run is gone, has not started within `start-grace`, the scheduler is paused, or `hook-wait` has passed. Judge runs do not count against `max-concurrent` (their own slots bound them), so task work never holds a session's stop.

### Closing a session's work (project-space spec, Phase C; from GitHub, remote-first spec §7.4)
A judge's `verify` is a claim; orange checks it from GitHub, never from the session's checkout, which it neither reads nor writes. At each stop the reporter says what the checkout is at (`payload.head_sha`, and `payload.dirty_files`: its `git status --porcelain` lines); the session keeps both (`sessions.head_sha`, `dirty_files`). The session is `verifying` and its stop hook goes on waiting while `SessionClosing` runs these steps as runs of the session (`runs.attended_session_id`), each queued by the one before:
- **`verify`** (`EvidenceRunner` → `SessionChecks`, orange's own code): the stop's uncommitted files are a gap; then orange fetches the repo's mirror, and the head must be on the session's branch on GitHub (pushed further since is fine), else the gap is "push `<branch>` and stop again". A session on the base branch itself pushes to a side branch `orange/session/<last 8 hex of its id>` instead (builder's call 11). The head is kept in the mirror as `refs/orange/sessions/<id>`; every command of the project's `evidence` convention runs on a clone of it under the run's directory (in container mode each in a container of its own), with only the allowlisted environment; the first failure ends the check. Each check is an `evidence` row with `session_id`.
- **`diff_review`**: the diff since the work left its base, read from the mirror, against the session's intent, only when the `review` convention asks for one (`risky`, the default, reviews a diff that touches the risk paths). Like the judge it has no built-in tools and runs in an empty directory; the diff is in its prompt. Skipped when there is no base or no diff, and carried over a clean rebase.
- **`integrate`** (`Integrator`, the same code as for tasks): per the `integration` convention. `merge` works in a scratch worktree of the mirror at the verified head. A branch that already has the base is pushed as it is, with its SHAs (builder's call 9); otherwise it is rebased as orange's bot (the authors stay), the rebased commit, which exists only in the mirror, goes back through `verify`, and then the base is pushed. orange never rewrites the user's branch on GitHub and never moves anything in the user's checkout: their next pull brings the base along. Work from a side branch fast-forwards the base to it, is pushed, and the side branch is deleted (only while it is still at the verified head: later work on it stays); when the base has commits the session lacks, the session is told to pull them in (`behind`). `remote-push` off closes the work as `verified` where it is. `branch` leaves the work where it is; `ask` and `pr` (not built) close it as verified and file a `session_integration` item.
- **Ends**: a gap at any step (uncommitted files, unpushed work, a failing command, review gaps, a rebase conflict, a base the session is behind) becomes a `continue` verdict, so the stop hook sends it back into the session; it counts towards the loop guard and is not recorded as a decision. A pass closes the work: `session_work` gets its result (`integrated` or `verified`) and note, the session is `closed`, and the hook lets it stop. The next prompt opens new work with that prompt as the intent (spec decision 10). When nothing can be checked (no GitHub remote, a detached head, a stop that did not say its head, a broken convention, a failed run), the session just stops as finished.
- **Conventions** (`WorkConventions`, session → project → global): `done` (default `[evidence, integrated]`; `[committed]` and `[]` need no commands, and `[committed]` no push), `integration`, `evidence`, `base-branch` (else the repo's default as a checkout reported it, else GitHub's), `remote-push`, `review` (`never`, `risky`, `always`).
- **No evidence commands, no close.** A project without an `evidence` convention cannot be verified: the session stops as before, orange files one `evidence_missing` item per project and proposes what `EvidenceDetector` found in the repo (at the session's head when GitHub has it). Evidence commands run the project's code, so only the user puts them in force (`orange_accept`, `orange_set`); orange never accepts its own proposal. Until a project has them, orange integrates nothing there, a session's work or a task's.
- **The user and time**: a prompt cancels the queued step and voids the running one's result. A check may outlast the hook's wait: a late pass still closes and integrates, a late gap expires into a `session_question` item with the gap as the proposed answer. `GET /sessions/{id}/work` shows a session's work and evidence.

### The focus brief (project-space spec, Phase D)
A brief is facts plus words. orange reads the facts itself; a short `brief` run adds the words. A run that fails, is skipped or is refused costs the words, never the brief.
- **Facts** (`BriefSnapshots`, one repeatable-read transaction; stored as `briefs.snapshot`): for each active project its goals, milestones (days left, share of its time gone, work closed since it was set), sessions and their states, the work closed and the user's prompts since the last scheduled brief, open attention items and its rhythm; outside the projects, other open items and orange's own tasks. The twelve most recently active projects get facts, further active ones are named, proposed and paused ones counted. `Quiet` decides "quiet": silent for longer than the project's `cadence` convention, or without one for longer than max(2 × its usual gap, its longest gap) over 60 days; under 3 active days is too new to judge. The model never writes a count, a date, the timetable or "quiet": `BriefText` prints them from the snapshot beside its lines.
- **The run** (`BriefService.write`): started directly and waited for (`WorkerRunner.runDirect`: no queue, no slot, no post-run step), role `brief` on the medium tier at low effort, 5 minutes, no built-in tools, in an empty directory. `BriefPrompt` puts orange's facts and the user's own words first; what sessions and agents wrote (intents, branch names, titles) comes last, one line per ref, inside a fence named by a per-run random id. The run ends with `submit_brief` on `/mcp/worker`: a `status_line` per project, up to three `focus` items, rarely an `urgent` entry. `BriefContent.parse` refuses a project that is not in the run's list, a missing or repeated project, blank or over-long text, line breaks, control and invisible characters (bidi marks, zero-width ones), links (any `scheme://`, or `www.`) and more than three focus or urgent entries; a refused call records nothing. `runs.input` holds only the trigger, the brief time and the project names.
- **No model lines**: the brief is then written from the facts by rule, with a note saying why: nothing new since the last brief (no run and no push), the scheduler is paused (no run), the run failed or submitted nothing valid, or a run for that brief time already exists. A brief time gets one model attempt, never a retry.
- **Schedule** (`BriefScheduler.sweep` every `orange.brief.sweep`, one tick at a time on a thread of its own; each step reads the time again, since a brief run takes minutes): `BriefSchedule.due` takes the latest time of the global `brief-times` convention at or before now. A time inside quiet hours is skipped, not deferred, and a missed one is written only within `catch-up` (2h): downtime gives one brief, never a backlog. `briefs.slot_at` is unique, so a second tick or a restart writes nothing. A brief covers what happened since the previous scheduled brief (the first: `first-window`). Briefs older than `retention` are deleted, also with `orange.brief.enabled` off (`orange_focus` still writes some).
- **Delivery** (`BriefDelivery`): a scheduled brief with something new goes to ntfy's `brief-topic` at priority 3 (no topic set: the attention topic; there is no built-in name, which on a public server anyone could guess), with a link to its page when `orange.brief.public-url` is set. It counts as delivered only when ntfy took it; a failed push is tried again at the next tick, never in quiet hours and never after `catch-up`. A brief that was asked for is not pushed, and with `orange.notify.enabled` off nothing is.
- **Urgent entries** become `normal` attention items of kind `brief_urgent`: at most one unresolved per project, never pushed on their own, never raising an existing item. The model cannot page the phone.
- **The page** (`BriefPageController`, `BriefText.html`; no script, every stored value escaped): the brief, then the facts it was written from. `GET /brief` is the latest one (API token). `GET /brief/{id}?k=<page key>` opens with the brief's own key for `link-ttl` (48h), or with the API token; a wrong key, an expired key and an unknown id are the same 404.
- **`orange_focus`** (`/mcp/steering`): returns the latest brief (its text, its page, whether it has model lines) and never starts a run. `fresh: true` writes one, at most every `fresh-min-interval` (10m, checked again under the write lock), and waits `focus-wait` (60s) for it; after that it answers `writing` and the brief is there at the next call. A paused scheduler gives the facts at once; with no active project there is nothing to write.

### Plans and approval (remote-first spec §7.2)
- **`orange_plan` returns at once** with the plan's id, `planning` (refused while the scheduler is paused). `PlanService` plans in the background (`plan` run, started directly) with the project's facts in the prompt (`PlannerPrompt`: repos, base branch, goals, milestones, decisions, notes, evidence in force, the `review` convention) and a clone of `origin/<base>` of its mirror at `repo/` in the planner's directory (`core.symlinks=false`: committed links come as plain files; deleted when the planner is done); orange runs no git there after the clone, and the planner has no Bash. What is under `repo/` is data, never instructions (`planner.md`, `PlannerPrompt`). In container mode the planner runs in a container; on the host it has no `WebFetch` while it reads the clone. The clone is the project's first GitHub repo, and a plan's tasks go there unless the plan or a task names another `repo` of the project. A revision carries the plan it revises (its tasks and order) and every note along its `revises_id` chain, oldest first.
- **Then orange's rule** (`PlanApproval`, pure; first match wins): no evidence in force asks (approving is how its proposed commands go in force, builder's call 12); the `plan-approval` convention `always` asks and `never` dispatches; under `auto` the planner's `ask_first`, a risky task (`risk` plus `risk_reason`) or more than `orange.planner.ask-above-tasks` tasks ask. Otherwise the plan dispatches: its tasks remember the plan and the milestone (`tasks.plan_id`, `milestone_id`).
- **Asking is one urgent `plan_approval` item** (`PlanText`: the tasks with their risk marks, the order, why it asks, the proposed evidence, each command on its own line in backticks). Proposed commands with a line break, a control or format character (bidi, zero-width), over 300 characters, or more than 5 of them are refused as a whole (`PlanJson.evidenceRefusal`): the plan carries none, and the item says why. `orange_resolve` acts through `AttentionResolver` in the resolve's transaction: `approve` puts the proposed evidence in force as the user's (only when none is) and dispatches; `drop` drops; any other text drops it and plans the request again with the text as the note (`revises_id`). The plan row moves `asking → dispatched` under its row lock, and a resolved item resolves no more, so a plan dispatches once.
- **A plan that cannot finish** (the planner failed or wrote nothing valid, ingest refused it, orange restarted while it was `planning`) is `failed` with a reason and files a normal `plan_failed` item.

### Stuck tasks ask for a person (remote-first spec §7.5, builder's call 13)
- **`needs_human` files one urgent `task_needs_human` item** (`TaskAttention`), whatever sent it there: a blocked report, a `request_human`, the reactor giving up, a failed integration. It names the task, the project, why in words and the last events; the reactor's give-up files it after its transaction commits, never under the task's lock. Nothing sets `failed` today, so there is no item for it yet.
- **The answer reopens the task** with the answer as its note, which the next implement prompt carries; a blank answer only dismisses the item. A reopen over REST or a cancel resolves the item instead, so no stale question waits.
- **Its branch goes to GitHub** as `orange/task/<short id>` (`StuckBranches`, force-pushed from the task's worktree, only when remote push is on), so the user can look from the laptop; it is deleted from the mirror once the task is integrated or cancelled. Neither ever fails its caller.

### Milestones on track or behind (remote-first spec §7.6)
- **Tasks remember the milestone they serve** (`tasks.milestone_id`: the request's, or the planner's match). `MilestoneTracks` counts a milestone's tasks through its supersede chain (only accepted items move it), so editing a milestone keeps its tasks and a dropped or done one has none.
- **`OnTrack` (pure) labels a dated milestone with tasks:** `behind` when one of its tasks is stuck, or the share merged trails the share of its time gone by more than `orange.brief.on-track-margin` (0.20); otherwise `on_track`. Undated or taskless: no label. The brief, `orange_status` and the start context all print orange's label; the model is told it and never makes one.
- **Tasks show under their projects** in the brief and the status (merged, running, stuck, not started), with at most 3 stuck titles per project in the brief.

### The steering tab (remote-first spec §7.5, decision 8)
- **One Claude Code session the user talks to orange in**, started with `ORANGE_STEERING=1` or in `ORANGE_STEERING_DIR` (default `~/.orange/steering`; the reporter compares real paths). The reporter adds `steering: true` to every event of it.
- **Recorded, never judged** (`sessions.steering`, sticky once seen): no project is resolved from its cwd, and it counts as muted for the reactor and the sweeper, so no judge, no items, no idle filing. Its stops are the user talking to orange, not work.
- **It starts from facts.** At its `SessionStart` the reporter asks `GET /steering/context` (API token; `200 text/plain`, at most 8 lines: the pause, a line per active project, what waits for the user, a hint) in what is left of its 2 s, only when orange took the start event, and prints it as the hook's `additionalContext`; anything else prints nothing. Nothing lives in the tab: projects, plans, tasks and questions are in orange, so it can be cleared at any time.

### Orange data model
Flyway migrations live under `orange/src/main/resources/db/migration/` (immutable once merged; add `V<n+1>__…` files):

- **`tasks`** — DAG of work units (each of a project and one of its repos, `project_id`/`repo_id`, or of neither: the legacy base repo) with the evidence-gated lifecycle (`pending → ready → running → verifying → verified → integrated`, plus `needs_human`, `failed`, `cancelled`; see `TaskStatus` and the project-space spec §10). A child becomes `ready` when every parent is `integrated` (trigger `promote_ready_dependents`). `branch` and `head_sha` are what verification and integration work from; `pr_number`/`pr_url` are for the later PR mode; `failures` counts model failures; `plan_id` and `milestone_id` are the plan a task came from and the milestone item it serves. Every status change fires `pg_notify('task_changed', <id>)`.
- **`runs`** — one row per run: kind, status, role, attempt, route (tier, model, effort, auth, budget), lease, pid, MCP token hash, gateway key alias, cost and tokens, `input` (head or feedback) and `outcome`. Inserts fire `run_queued`, status changes `run_changed`. **`run_events`** holds each run's event stream; **`settings`** holds the scheduler pause.
- **`evidence`** — every check orange ran on a head of a task or of a session (`task_id` or `session_id`), and every diff review of it.
- **`session_work`** — the pieces of work in a session, one open at a time: intent, how it closed (`integrated`, `verified`), head, branch, base and orange's note.
- **`plans`** — one per request to plan (`project_id`, the user's `request`, a revision's `note` and `revises_id`): `planning → dispatched`, or `asking` (its `plan_approval` item, `attention_id`) `→ dispatched | dropped`, or `failed` (`failure`); orange's decision (`ask_first`, `reason`), the planner's `plan` and `architecture`, `milestone_id`, `run_id`.
- **`events`** — the inbox (webhook deliveries and session events, once per delivery id); inserts fire `event_received`.
- **`projects`**, **`project_repos`** — projects (`proposed`, `active`, `paused`, `archived`) and the checkouts that map sessions to them (unique per node and path; `repo_id` when the checkout's remote is on GitHub).
- **`repos`** — a project's GitHub repos, unique by `key` (`owner/name`), with the default branch a checkout reported. orange mirrors each one.
- **`space_items`** — the project space: kind, body, status (`proposed`, `active`, `done`, `dropped`, `superseded`), author, `supersedes_id`; one active value per convention key, per project and per session override.
- **`sessions`**, **`session_events`** — the user's sessions (unique per harness and its session id), why and since when each waits, what its last stop said of its checkout (`head_sha`, `dirty_files`), whether it is the steering tab (`steering`), and the events applied to it. Status changes fire `session_changed`.
- **`verdicts`** — one per judged stop (`session_id`, `stop_event_id`): kind (`continue`, `verify`, `escalate`, `idle`), message, rationale, confidence, status (`pending`, `delivered`, `cancelled`, `expired`).
- **`briefs`** — one row per focus brief, written once and complete: `slot_at` (the brief time, unique; null when it was asked for), `snapshot_at` and `snapshot` (the facts), `content` (the model's lines; null = facts only) and `note` (why), `run_id`, `pushable`, `page_key`, `delivered_at`.
- **`attention_items`** — the inbox: kind, urgency, status, a `dedupe_key` that is unique forever, `pushed_at`. A new item or a raised urgency fires `attention`.
- **`dev_envs`** — leasable port-pool envs (5 pre-seeded; dormant until UI QA). Returning to `free` fires `pg_notify('dev_env_freed', ...)`.

When adding or modifying tables, follow the existing patterns: `uuidv7()` PKs, `touch_updated_at()` trigger, partial indexes on hot-status queues, `pg_notify` on state changes that callers might `LISTEN` for.

### Deploy (remote-first spec R3)
orange runs on one Linux host, the laptop runs only the plugin. `deploy/vps/setup.sh` (idempotent) sets up:
- the user `orange` (in the `docker` group, never root) and `orange.service` (systemd, `java -jar`, container mode); a new jar that does not get healthy is swapped back;
- Postgres and ntfy in compose on 127.0.0.1 (ntfy: no anonymous access, `upstream-base-url` ntfy.sh for the iPhone);
- the run network with a fixed subnet and its bridge `orange-runs0`, orange listening on 127.0.0.1 plus that gateway;
- Claude Code on the host at the worker's pinned version (plan, brief, judge) and the worker image built as `orange`;
- `tailscale serve` (443 → orange, 8443 → ntfy), ufw (incoming only SSH, Tailscale and the run bridge to orange's port), runs kept off the tailnet and private ranges (`run-egress.sh`), and sshd keys only;
- then it checks it all, from loopback and from a container on the run network. Nothing host-specific is committed: the tailnet name is read on the host.

### Webhook ingress
`POST /webhooks/github` is HMAC-authenticated by `GithubWebhookHmacFilter` (verifies `X-Hub-Signature-256` against `orange.github.webhook-secret`); the filter wraps the request via `CachedBodyHttpServletRequest` so the controller can re-read the body. The controller only stores the delivery in the `events` inbox and answers 200 `{stored}`; `EventProcessor` handles stored events one per transaction in id order and parks an event after 5 failed attempts. `GithubEventHandler` only logs: orange integrates verified work itself, and webhooks change tasks only in the later PR integration mode. Security config (`SecurityConfig`) permits this path and lets the HMAC filter authenticate; CSRF is disabled because there are no browser-form writes.

### Operator API
`/tasks` (create, list, events, reopen, replay, cancel — cancel also cancels queued runs and kills the running one), `/tasks/{id}/runs`, `/tasks/{id}/evidence`, `/runs/{id}`, `/runs/{id}/events`, `/events/live` (running runs with their latest events), `/health/aggregate`, `/scheduler`, `/plans`, `/dispatch`, `/dev-envs`. They want `ORANGE_API_TOKEN` when it is set (see Auth above); without it, bind orange to localhost. In container mode on Linux orange has to listen where the run network reaches it: the VPS sets `server.address=127.0.0.1` and `orange.server.extra-addresses` to the run network's gateway, and ufw keeps the port closed to everything but that bridge; `RunNetworkGuard` keeps the runs themselves to `/mcp/worker`.

### Spring config
- App config lives in `orange/src/main/resources/application.yaml`. Notable knobs: `orange.runs` (loop switch, worker id, slots and timeouts per kind, lease TTL, heartbeat, sweeps, retention), `orange.evidence` (commands, output tail), `orange.integration.remote-push`, `orange.events` (processing switch, poll, max attempts), `orange.api.token`, `orange.attention` (sweep, escalation and idle times), `orange.judge` (switch, hook wait, loop guard, pickup grace), `orange.brief` (switch, sweep, catch-up, first window, the fresh brief's interval and wait, public url, link lifetime, retention, `on-track-margin`), `orange.planner.ask-above-tasks` (a larger plan asks first), `orange.notify` (batch window, zone, ntfy and its attention and brief topics), `orange.conventions` (global defaults, `plan-approval` among them), `orange.routing` (tiers, rules, risk paths, escalation), `orange.harness` (run root, Claude Code command, env allowlist), `orange.runner` (`isolation`: `process` or `container`; under `container` the docker command, the image, how the image starts Claude Code, the network, the host's address for runs (`host-address`), the user, the home directory, memory, cpus and pids limits, extra volumes), `orange.billing` (subscription token, prices), `orange.gateway` (LiteLLM URL, master key, timeouts), `orange.mcp.worker-url`, `orange.server.extra-addresses` (more listen addresses beside `server.address`), `orange.repos` (mirrors root, GitHub URL, GitHub's API URL (`github-api-url`, `ORANGE_GITHUB_API_URL`), tokens per owner), `orange.worktrees` (root, the legacy base repo and base branch for tasks of no repo, max count), `orange.github.webhook-secret`. All take env-var overrides.

## Environment / secrets

- `orange/.env` is read by `bootRun`/`test`, docker compose and the webhook-forward script; it is `.gitignore`d. `orange/.env.example` lists every key. For end-to-end runs: `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`), `ORANGE_GITHUB_TOKENS` (a fine-grained PAT per owner, `owner=token[,owner=token]`: Contents read/write, Metadata read, and Administration read/write for `orange_project_create` to create repos) with `ORANGE_REPOS_ROOT` (blank: `~/.orange/repos`) for project repos, `WORKTREES_BASE_REPO` for tasks of no project, and for webhooks `GITHUB_WEBHOOK_SECRET`, `GITHUB_ORG` / `GITHUB_REPO` for the forwarder. `LITELLM_MASTER_KEY` and `ANTHROPIC_API_KEY` are only needed for gateway tiers. `ORANGE_RUNNER_ISOLATION=container` runs a task's runs in containers from the image `./worker/build.sh` built (`ORANGE_WORKER_IMAGE` when it is not `orange-worker:local`); blank means process mode. `ORANGE_NTFY_URL` (plus topic and token) turns pushes on; the brief goes to `ORANGE_NTFY_BRIEF_TOPIC` (blank: the attention topic), carries a link to its page when `ORANGE_PUBLIC_URL` says where a phone reaches orange, and `ORANGE_BRIEF_ENABLED=false` switches the scheduled briefs off; `ORANGE_API_TOKEN` guards the operator API, and the plugin's hooks and MCP entry read the same variable from Claude Code's environment, with `ORANGE_URL` (and `ORANGE_STEERING`, `ORANGE_STEERING_DIR` for the steering tab). `ORANGE_SERVER_EXTRA_ADDRESSES` and `ORANGE_RUNNER_HOST_ADDRESS` are for Linux in container mode. On the VPS all of it lives in `/etc/orange/orange.env`, which `deploy/vps/setup.sh` writes (see `deploy/README.md`); the laptop's `orange/.env` then only holds the two secrets `push-secrets.sh` sends.
- Do **not** check `.env` files in.
