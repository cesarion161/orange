# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

- **`orange/`** — Java 27 / Spring Boot 4 coordinator. Owns persistence (Postgres + Flyway + jOOQ), task state and the run loop: it starts Claude Code (`claude -p`) directly, one process per agent run, verifies the work itself and integrates it. No Temporal, no external workers.
- **`orange-mcp/`** — Python stdio MCP shim the Claude Code plugin uses to call orange's task REST API (until v2 PR 5 folds those tools into `/mcp/steering`).
- **`plugin/`** — the Claude Code plugin: the session reporter (`hooks/hooks.json`, `hooks/orange-report.py`), the steering MCP entry (`.mcp.json`) and the skills. The repo root is its marketplace (`.claude-plugin/marketplace.json`, name `orange-local`); the task tools' Python server is in the repo's own `.mcp.json`, not in the plugin, because an installed plugin is a copy outside the repo.
- **`docs/superpowers/`** — the v2 design spec, the project-space spec that amends it, and per-PR implementation plans.

Inside `orange/src/main/java/com/ai/orange/`:
- **`run/`** — the run loop. `RunRepository` (runs with leases), `TaskReactor` + `ReactorDecision` (each task's next run), `RunScheduler` (per-kind slots), `RunReaper` (expired leases, orphans of a previous instance), and the three executors: `WorkerRunner` (agent runs), `EvidenceRunner` (verify) and `Integrator` (integrate). `RunPreparer` builds prompts, `PostRunSteps` applies a run's effects, `FailureReasons` classifies failures, `SchedulerPause` is the stop switch, `SpendSync` and `RunRetention` keep house.
- **`harness/`** — harness-neutral run model (`RunSpec`, `RunEvent`, `HarnessAdapter`, `ProcessRunHandle`) and **`harness/claude/`**, the Claude Code adapter (`ClaudeCodeCommand` builds argv + env, `StreamJsonParser` reads `--output-format stream-json`).
- **`roles/`** — `RolePrompts` (role instructions from `src/main/resources/roles/*.md`) and `ToolPolicy` (tools per run kind).
- **`mcp/`** — the worker MCP endpoint `/mcp/worker` (`WorkerTools`: `report_result`, `request_human`, `submit_review`, the judge's `judge_continue` / `judge_verify` / `judge_escalate` / `judge_idle` and `propose_item`) with per-run bearer tokens.
- **`project/`** — projects, their repos and the project space: `ProjectService` (repo → project, proposed projects), `SpaceService` (goals, milestones, decisions, notes, questions; items supersede, agents only propose) and `Conventions` (session → project → global).
- **`session/`** — the user's own interactive sessions: `NeutralEvent` (what reporters post), `SessionReactor` (the pure rule table), `SessionService` (applies events, files attention), `SessionSweeper`, `QuestionDetector`, `SessionJudgement` (the judge's verdicts) and `SessionClosing` (verify, review, integrate and close a session's work).
- **`attention/`** — the attention inbox (`AttentionService`): everything that wants the user, once per dedupe key.
- **`notify/`** — `PushPlanner` (urgency, batch window, quiet hours), `NtfyClient`, `AttentionNotifier`.
- **`mcp/`** also holds the steering endpoint `/mcp/steering` (`SteeringTools`).
- **`evidence/`** — evidence rows, the configured evidence commands, the `evidence` convention (`EvidenceCommands`) and `EvidenceDetector` (what a repo suggests).
- **`events/`** — the inbox (webhooks are stored first, processed later) and its processor.
- **`routing/`** — the rule table: role × difficulty × risk × prior failures → tier (model, harness, auth, budget) + effort.
- **`gateway/`** — LiteLLM admin client (per-run virtual keys, spend by alias, timeouts).
- **`billing/`** — price table, cost estimate, plan-limit detection and reset time.
- **`worktree/`** — per-task git worktrees (`WorktreeService`) and the one git helper (`Git`).

## Common commands

Run from `orange/`:
- **Run app**: `./gradlew bootRun` — automatically loads `orange/.env` into the process env (see `parseDotEnv()` in `build.gradle.kts`). Copy `orange/.env.example` to start.
- **jOOQ codegen**: runs automatically before `compileJava` via the `nu.studer.jooq` plugin. The `generateJooq` task spins up an embedded Postgres 18 (no Docker needed), runs all Flyway migrations against it, then generates Java sources under `build/generated/sources/jooq/main/java` in package `com.ai.orange.db.jooq`. To regenerate after editing a migration, just `./gradlew generateJooq`.
- **All tests**: `./gradlew test` — JUnit 5 + Testcontainers (Postgres 18). Needs a running Docker daemon and nothing else (no Temporal, no model calls). The run loop and the events processor are off in tests (`src/test/resources/config/application.yaml`); `RunLoopE2EIT` turns them on and takes a task from ready to integrated. `SessionCloseIT` verifies, integrates and closes session work on temporary git repositories. `SessionReporterIT` runs the plugin's real reporter script (needs `python3`) on captured hook payloads from `src/test/resources/hooks`.
- **Live tests** (tagged `live`, excluded from `test`): `./gradlew liveTest`.
  - `ClaudeCliContractLiveIT` runs the installed `claude` with orange's full command line and an invalid token (no secret, no model call); rerun it after Claude Code updates itself.
  - `WorkerMcpRealClaudeLiveIT` checks that the real `claude` connects to `/mcp/worker` and sees the run's tools (invalid token, no model call).
  - `SubscriptionSmokeLiveIT` makes one tool-less Haiku call on the Max plan (needs `CLAUDE_CODE_OAUTH_TOKEN`).
  - `LiteLlmGatewayLiveIT` exercises the virtual-key lifecycle and the alias lookups against a running LiteLLM (needs `LITELLM_MASTER_KEY`), with no model calls.
- **Single test class**: `./gradlew test --tests com.ai.orange.run.TaskReactorIT`
- **Build**: `./gradlew build`
- **Local infra (Postgres + Grafana LGTM)**: `docker compose up -d`. Spring Boot's `spring-boot-docker-compose` dev dependency also brings these up when running `bootRun` with the `dev` profile.
- **LiteLLM gateway** (only for routing tiers with `auth: gateway`): `docker compose --profile gateway up -d litellm`. It refuses to start without `LITELLM_MASTER_KEY`; `litellm-db-init` creates its database on existing Postgres volumes.
- **Run with Testcontainers-managed Postgres instead of compose**: `./gradlew bootTestRun` using `TestOrangeApplication`.
- **Forward GitHub webhooks to localhost during dev**: `./scripts/forward-webhooks.sh` (requires `gh` + `gh-webhook` extension; reads `GITHUB_ORG` xor `GITHUB_REPO` and `GITHUB_WEBHOOK_SECRET` from `.env`).

The Java toolchain (JDK 27) is provisioned automatically by the foojay resolver if it isn't installed.

Docker socket note: tests on macOS auto-detect `~/.docker/run/docker.sock` and set `DOCKER_HOST` / `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE` for Testcontainers — see `tasks.withType<Test>` in `build.gradle.kts`.

## Architecture

### The run loop
Every unit of agent or verification work is a `runs` row (kinds `plan`, `implement`, `ci_fix`, `verify`, `diff_review`, `integrate`, `judge`; `brief` comes with project-space phase D). A task has at most one queued or running run (partial unique index).
- **`TaskReactor`** reacts to `task_changed` / `run_changed` (and sweeps every `orange.runs.reactor-sweep`). It locks the task row and applies `ReactorDecision`, a pure rule table: `ready` → implement; `running` → a `ci_fix` after verify gaps, an integration conflict or a failed fix, otherwise implement (with review gaps, or the failed attempt's own feedback); `verifying` → verify, then diff review, then `verified`; `verified` → integrate. Too many failures (`orange.routing.escalation.needs-human-after-failures`) or a worktree that moved under orange → `needs_human`. Nothing happens while paused.
- **`RunScheduler`** claims queued runs (on `run_queued`, when a run ends, and every `scheduler-poll`) up to each kind's slots and `max-concurrent`, and runs each on a virtual thread. Plan runs (`WorkerRunner.runDirect`) take no slot.
- **Leases**: a running run renews its lease every `heartbeat`; `RunReaper` fails expired leases (`lease_expired`) and, at startup, kills and fails runs a previous instance left running (`coordinator_restart`). Neither counts against the task.
- **Ordering rule**: a run stays `running` until its post-run steps (`PostRunSteps`) have landed, so the reactor never queues a task's next run on half-applied state.
- **`SchedulerPause`**: failures that would recur at once pause the scheduler — a plan limit until its reset time, a rejected or missing token until resumed, the gateway down for 5 minutes, a missing binary or broken workspace until resumed. `GET /scheduler`, `POST /scheduler/pause|resume`.

### Running Claude Code (`WorkerRunner`)
1. **Prepare** (`RunPreparer`): the task's worktree (`WorktreeService.ensure` keeps earlier attempts' commits) and a prompt — the task, the operator's reopen note, `input.feedback` to address, how earlier attempts ended, and the base the branch integrates onto. A diff review gets the intent and the whole diff instead (cut at 200,000 characters).
2. **Route** (`RoutingTable`, `orange.routing`) to a tier (model, harness, auth, budget) and an effort. Two failures move the run one tier up (or raise effort at the top tier); risky tasks get at least the large tier.
3. **Credentials** by the tier's `auth`:
   - `subscription` (default): the Max-plan token from `claude setup-token` (`CLAUDE_CODE_OAUTH_TOKEN`); Claude Code talks to Anthropic directly. Anthropic's terms restrict subscription tokens to Claude Code itself, so the token goes only into the `claude` child's environment — never to LiteLLM, logs, `run_events`, `task_events` or `runs`.
   - `gateway`: a LiteLLM virtual key minted for this run (`GatewayClient`), limited to the run's models and budget, always blocked when the run ends; `SpendSync` later books its final spend and deletes it.
4. **MCP**: agent kinds that report get a per-run token (only its SHA-256 is stored) in a `mcp.json` passed as `--mcp-config` and deleted afterwards. Outcomes come only from `/mcp/worker` (`report_result` done|blocked|failed, `request_human`, `submit_review` pass|gaps) — never parsed out of transcripts. Tools per kind come from `ToolPolicy` (implement/ci_fix edit and commit; diff_review is read-only with no Bash).
5. **Start** `claude -p --output-format stream-json --verbose --model … --effort … --setting-sources project,local --strict-mcp-config …`. The prompt goes on **stdin** (never argv). The child environment is built from an allowlist (`orange.harness.claude-code.pass-env`); credential-like variables are dropped even if allowlisted, and `CLAUDE_CONFIG_DIR` points at a per-run directory under `orange.harness.run-root` so the user's own Claude Code login, plugins and hooks never load. The credential and the MCP token are redacted from everything the run writes.
6. **Watch**: events go to `run_events` (`init`, `assistant`, `tool_use`, `tool_result`, `result`, `api_retry`); subscription runs are killed when their estimated cost passes the tier budget; every run is killed at its kind's timeout. Kills take the whole process tree.
7. **Outcome**: no report → `no_outcome`, a `failed` report → `reported_failed`; `FailureReasons` decides what counts (model failures add to `tasks.failures`) and what pauses.

### Verification and integration (project-space spec §7–§8)
An agent's `done` only starts verification; evidence decides "done".
- **Implement done**: with commits on the branch, the head is recorded and the task moves to `verifying`; without, the run fails as `no_commits`.
- **`EvidenceRunner`** (`verify` runs, orange's own code): the worktree must be at the queued head and clean, and every `orange.evidence.commands` entry must pass, run as `sh -c` in the worktree with only the allowlisted environment. Each check is an `evidence` row; failures are gaps that send the task back for a `ci_fix` and count.
- **`diff_review`**: a read-only reviewer compares the diff with the intent; its verdict is evidence. `pass` → `verified`; gaps send the task back for rework and count.
- **`Integrator`** (`integrate` runs, merge mode, one at a time): rebase onto the base; a changed head goes back to `verifying` (the diff review carries over, the commands re-run); otherwise push the base when there is an origin (`orange.integration.remote-push`) and move the local base branch along (`merge --ff-only` in a clean checkout, `update-ref` when not checked out, left alone when dirty). A conflict goes back for a fix without counting; git trouble goes to a person. `integrated` promotes the task's dependents.

Isolation: in process mode Claude Code confines its file tools to the worktree but its Bash tool is not confined. Process mode is for local development; container isolation is the boundary for unattended runs (v2 plan, spec §16).

Tests never call a model: `orange/src/test/resources/fake-claude/FakeClaude.java` is a single-file program that speaks real stream-json and the worker MCP protocol, launched via `com.ai.orange.harness.FakeClaude.command()` / `FakeClaude.register(...)`. With `report_result` allowed it implements and commits; with `submit_review` allowed it reviews and passes. With `judge_continue` allowed it answers the session (`judge-verify` says the work is finished; put `[[fake:review-gaps]]` in a committed file to fail a session's diff review). Other scenarios are picked by `[[fake:<name>]]` markers in the prompt (`judge-unsure`, `judge-escalate`, `judge-verify`, `judge-idle`, `judge-propose`, `no-commit`, `report-failed`, `blocked`, `no-outcome`, `dirty`, `wrong-tool`, `review-gaps`, `error`, `hang`, `expensive`, `plan-limit`, `auth-failed`, `leak-env`, `plan`).

### Sessions, the project space and attention (project-space spec, Phase A)
orange also watches the sessions the user runs themselves. Nothing here starts an agent; the judge that answers a stopped session is Phase B.
- **Reporter**: the plugin's hooks run `plugin/hooks/orange-report.py`, which turns a Claude Code hook into a neutral event (`session_started`, `user_prompt`, `stopped`, `waiting`, `active`, `session_ended`) and posts it to `POST /sessions/events`. It resolves git itself (main checkout through the common git dir, worktree, branch, remote), always exits 0 and gives up on an unreachable orange after 2 s, so a session never depends on orange. It prints nothing, except the hook decision that carries orange's answer at a stop (below). `active` comes from PostToolUse, and only while a marker file under `~/.orange/node/waiting/` says the session was waiting.
- **Ingestion**: the controller validates and stores the event in the `events` inbox (source `session`, `delivery_id` = the reporter's event id); `SessionEventHandler` applies it through `SessionService.apply`, so events are idempotent, ordered and retried like webhooks.
- **Rules** (`SessionReactor`, pure): a stop whose last message asks something (`QuestionDetector`) files a `normal` item; so does a permission or input prompt. `SessionSweeper` makes either `urgent` after `orange.attention.waiting-escalate-after` without the user, and files a stop with nothing to ask after `idle-after`. A user prompt, activity or the session's end resolves the session's items. Sessions of an `archived` project file nothing.
- **Projects**: a session's repo decides its project. An unknown repo becomes a `proposed` project plus an attention item; resolving it with `confirm` activates the project, `ignore` archives it.
- **Space**: `space_items` are never edited in place — a change inserts an item that supersedes the old one. An agent's item starts `proposed`; only accepting it makes it active (and only then does a proposed convention replace the value in force).
- **Pushes**: `AttentionNotifier` sends open `urgent` and `critical` items to ntfy (`orange.notify.ntfy`), one push per `batch-window` with everything that queued up; quiet hours (the global `quiet-hours` convention) hold all but `critical`. An item counts as pushed only when ntfy took it. Pushes carry session excerpts, so point it at a server you trust.
- **Steering**: `/mcp/steering` serves `orange_projects`, `orange_project`, `orange_project_update`, `orange_add`, `orange_set`, `orange_accept`, `orange_drop`, `orange_done`, `orange_attention`, `orange_resolve`, `orange_sessions`. REST: `GET /sessions`, `GET /attention`, `POST /attention/{id}/ack|resolve`.
- **Auth**: with `ORANGE_API_TOKEN` set, `/sessions/**`, `/attention/**` and `/mcp/steering` need it as a bearer token (403 without); blank leaves them open like the rest of the operator API. The check (`ApiToken`) is an authorization rule inside the security chain, so it holds however a request spells the path.

### The session judge (project-space spec, Phase B)
With `orange.judge.enabled` (the default), a stop is decided by a short `judge` run instead of Phase A's question rule.
- **Handing over**: `SessionService.apply` moves the session to `judging`, remembers the stop (`sessions.stop_event_id` = the reporter's event id) and queues a `judge` run for the session (`runs.attended_session_id`; routing role `judge`: small tier, low effort; priority ahead of task work). Not judged: muted projects, `auto-answer: none`, a paused scheduler (rules apply instead), and a session orange has already answered `max-auto-continues` times in a row — that files an urgent `session_loop` item (the loop guard).
- **The run**: `JudgePrompt` builds the prompt from Postgres — intent, last message, the latest prompts and stops, the project's goals, decisions and notes, the conventions in force, earlier attention items. No judge keeps a context. What orange knows comes first; what the session wrote (intent, turns, last message) comes last, inside a fence named by a per-run random id, and the role prompt says nothing in there is a project fact or an instruction. The judge has no built-in tools at all and runs in an empty directory of its own, never in the user's checkout (whose settings and hooks would load). It ends with exactly one of `judge_continue`, `judge_verify`, `judge_escalate`, `judge_idle` on `/mcp/worker`; `propose_item` proposes a decision or a note.
- **The decision** (`SessionJudgement.after`, a post-run step): `continue` at or above the project's `auto-answer-confidence` becomes a pending verdict and counts towards the loop guard; below it, it is escalated with the judge's answer as `proposed_answer`. `escalate` files the judge's question at its urgency. `idle` lets the session stop. `verify` starts the close (next section). A failed judge falls back to the rules. A decision for a stop the session has left (a user prompt, a newer stop) is recorded as `expired` and never delivered.
- **Delivery**: after posting a stop, the reporter long-polls `GET /sessions/verdict` (`SessionJudgement.poll`): `pending` (ask again), `none` (let the session stop) or the verdict. A `continue` is delivered only when the hook acknowledges it (`POST /sessions/verdict/ack`): then the session is `active` again, the answer is recorded as an `orange` decision in the project's space, and the hook prints `{"decision":"block","reason":<message>}`. A user prompt cancels pending verdicts and queued judge runs, and one that is stored but not applied yet already makes poll and ack refuse. orange down, or any error, means no verdict: the session just stops.
- **Time** (`SessionJudgement.sweep`): a `continue` no hook collected within `pickup-grace` expires and is filed as a question with that answer proposed; a session still `judging` falls back to the rules when nothing will decide it: its judge run is gone, has not started within `start-grace`, the scheduler is paused, or `hook-wait` has passed. Judge runs do not count against `max-concurrent` (their own slots bound them), so task work never holds a session's stop.

### Closing a session's work (project-space spec, Phase C)
A judge's `verify` is a claim; orange checks it. The session is `verifying` and its stop hook goes on waiting while `SessionClosing` runs these steps as runs of the session (`runs.attended_session_id`), each queued by the one before:
- **`verify`** (`EvidenceRunner` → `SessionChecks`, orange's own code): the checkout must have nothing uncommitted or untracked, and every command of the project's `evidence` convention must pass at the session's head. The commands run in a scratch checkout of that commit (`git worktree add --detach` under the run's directory, removed afterwards), never in the user's working tree, with only the allowlisted environment; the first failure ends the check. Each check is an `evidence` row with `session_id`.
- **`diff_review`**: the diff since the work left its base, against the session's intent. Like the judge it has no built-in tools and runs in an empty directory; the diff is in its prompt. Skipped when there is no base or no diff, and carried over a clean rebase.
- **`integrate`** (`Integrator`, the same code as for tasks): per the `integration` convention. `merge` rebases the session's branch in its own checkout (it is clean and stopped), sends a changed head back through `verify`, pushes the base when there is an origin (`remote-push`) and moves the local base branch along. A session that worked on the base branch itself is only pushed: orange never moves refs under the user's tree. `branch` leaves the work where it is; `ask` and `pr` (not built) close it as verified and file a `session_integration` item.
- **Ends**: a gap at any step (uncommitted files, a failing command, review gaps, a rebase conflict, a base branch behind origin) becomes a `continue` verdict, so the stop hook sends it back into the session; it counts towards the loop guard and is not recorded as a decision. A pass closes the work: `session_work` gets its result (`integrated` or `verified`) and note, the session is `closed`, and the hook lets it stop. The next prompt opens new work with that prompt as the intent (spec decision 10). When nothing can be checked (no checkout, a detached head, a broken convention, a failed run), the session just stops as finished.
- **Conventions** (`WorkConventions`, session → project → global): `done` (default `[evidence, integrated]`; `[committed]` and `[]` need no commands), `integration`, `evidence`, `base-branch` (else the repo's default as the reporter saw it, else origin's), `remote-push`.
- **No evidence commands, no close.** A project without an `evidence` convention cannot be verified: the session stops as before, orange files one `evidence_missing` item per project and proposes what `EvidenceDetector` found in the repo. Evidence commands run on the user's machine as the user, so only the user puts them in force (`orange_accept`, `orange_set`); orange never accepts its own proposal. Until a project has them, orange integrates nothing there.
- **The user and time**: a prompt cancels the queued step and voids the running one's result. A check may outlast the hook's wait: a late pass still closes and integrates, a late gap expires into a `session_question` item with the gap as the proposed answer. `GET /sessions/{id}/work` shows a session's work and evidence.

### Orange data model
Flyway migrations live under `orange/src/main/resources/db/migration/` (immutable once merged; add `V<n+1>__…` files):

- **`tasks`** — DAG of work units with the evidence-gated lifecycle (`pending → ready → running → verifying → verified → integrated`, plus `needs_human`, `failed`, `cancelled`; see `TaskStatus` and the project-space spec §10). A child becomes `ready` when every parent is `integrated` (trigger `promote_ready_dependents`). `branch` and `head_sha` are what verification and integration work from; `pr_number`/`pr_url` are for the later PR mode; `failures` counts model failures. Every status change fires `pg_notify('task_changed', <id>)`.
- **`runs`** — one row per run: kind, status, role, attempt, route (tier, model, effort, auth, budget), lease, pid, MCP token hash, gateway key alias, cost and tokens, `input` (head or feedback) and `outcome`. Inserts fire `run_queued`, status changes `run_changed`. **`run_events`** holds each run's event stream; **`settings`** holds the scheduler pause.
- **`evidence`** — every check orange ran on a head of a task or of a session (`task_id` or `session_id`), and every diff review of it.
- **`session_work`** — the pieces of work in a session, one open at a time: intent, how it closed (`integrated`, `verified`), head, branch, base and orange's note.
- **`events`** — the inbox (webhook deliveries and session events, once per delivery id); inserts fire `event_received`.
- **`projects`**, **`project_repos`** — projects (`proposed`, `active`, `paused`, `archived`) and the repos that map sessions to them (unique per node and path).
- **`space_items`** — the project space: kind, body, status (`proposed`, `active`, `done`, `dropped`, `superseded`), author, `supersedes_id`; one active value per convention key, per project and per session override.
- **`sessions`**, **`session_events`** — the user's sessions (unique per harness and its session id), why and since when each waits, and the events applied to it. Status changes fire `session_changed`.
- **`verdicts`** — one per judged stop (`session_id`, `stop_event_id`): kind (`continue`, `verify`, `escalate`, `idle`), message, rationale, confidence, status (`pending`, `delivered`, `cancelled`, `expired`).
- **`attention_items`** — the inbox: kind, urgency, status, a `dedupe_key` that is unique forever, `pushed_at`. A new item or a raised urgency fires `attention`.
- **`dev_envs`** — leasable port-pool envs (5 pre-seeded; dormant until UI QA). Returning to `free` fires `pg_notify('dev_env_freed', ...)`.

When adding or modifying tables, follow the existing patterns: `uuidv7()` PKs, `touch_updated_at()` trigger, partial indexes on hot-status queues, `pg_notify` on state changes that callers might `LISTEN` for.

### Webhook ingress
`POST /webhooks/github` is HMAC-authenticated by `GithubWebhookHmacFilter` (verifies `X-Hub-Signature-256` against `orange.github.webhook-secret`); the filter wraps the request via `CachedBodyHttpServletRequest` so the controller can re-read the body. The controller only stores the delivery in the `events` inbox and answers 200 `{stored}`; `EventProcessor` handles stored events one per transaction in id order and parks an event after 5 failed attempts. `GithubEventHandler` only logs: orange integrates verified work itself, and webhooks change tasks only in the later PR integration mode. Security config (`SecurityConfig`) permits this path and lets the HMAC filter authenticate; CSRF is disabled because there are no browser-form writes.

### Operator API
`/tasks` (create, list, events, reopen, replay, cancel — cancel also cancels queued runs and kills the running one), `/tasks/{id}/runs`, `/tasks/{id}/evidence`, `/runs/{id}`, `/runs/{id}/events`, `/events/live` (running runs with their latest events), `/health/aggregate`, `/scheduler`, `/plans`, `/dispatch`, `/dev-envs`. No auth yet: bind it to localhost.

### Spring config
- App config lives in `orange/src/main/resources/application.yaml`. Notable knobs: `orange.runs` (loop switch, worker id, slots and timeouts per kind, lease TTL, heartbeat, sweeps, retention), `orange.evidence` (commands, output tail), `orange.integration.remote-push`, `orange.events` (processing switch, poll, max attempts), `orange.api.token`, `orange.attention` (sweep, escalation and idle times), `orange.judge` (switch, hook wait, loop guard, pickup grace), `orange.notify` (batch window, zone, ntfy), `orange.conventions` (global defaults), `orange.routing` (tiers, rules, risk paths, escalation), `orange.harness` (run root, Claude Code command, env allowlist), `orange.billing` (subscription token, prices), `orange.gateway` (LiteLLM URL, master key, timeouts), `orange.mcp.worker-url`, `orange.worktrees` (root, base repo, base branch, max count), `orange.github.webhook-secret`. All take env-var overrides.

## Environment / secrets

- `orange/.env` is read by `bootRun`/`test`, docker compose and the webhook-forward script; it is `.gitignore`d. `orange/.env.example` lists every key. For end-to-end runs: `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`), `WORKTREES_BASE_REPO`, and for webhooks `GITHUB_WEBHOOK_SECRET`, `GITHUB_ORG` / `GITHUB_REPO` for the forwarder. `LITELLM_MASTER_KEY` and `ANTHROPIC_API_KEY` are only needed for gateway tiers. `ORANGE_NTFY_URL` (plus topic and token) turns pushes on; `ORANGE_API_TOKEN` guards the session and steering endpoints, and the plugin's hooks and MCP entry read the same variable from the user's shell, with `ORANGE_URL`.
- Do **not** check `.env` files in.
